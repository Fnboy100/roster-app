fix(frontend): route Floor/Kitchen export through the backend's normalized roster; add Kitchen to the engine

Floor's PDF export was rendering empty tables and its CSV was missing
hours/totals/variance entirely — root cause was two hardcoded,
Bar-specific constants in utils/exportPDF.js/exportCSV.js and a lossy
client-side roster mapping that dropped shift_code/hours before export
ever saw them (see the backend commit for the full root-cause writeup).
Rather than patch those constants for Floor specifically, engine-managed
departments now export through the new backend endpoint that reads the
exact same normalized rows the on-screen table does; Bar/Stewarding/
Store keep their original, completely untouched exportCSV.js/exportPDF.js
path.

- api/rosterEngine.js: new exportRoster(periodId, format) — GET
  /roster/engine/periods/{id}/export?format=csv|pdf as a blob download,
  same pattern already used for presence-violation CSV export. Reads
  the real filename from the response's Content-Disposition header
  instead of hardcoding one. Also new getNormalizedRoster(periodId) for
  anything that wants the same rows without triggering a file download.

- pages/RosterApp.jsx:
  - CSV/PDF buttons now branch: isEngine departments call the new
    handleExport('csv'|'pdf') (backend-normalized download, works
    identically for a roster generated this session or reloaded from a
    save), everything else calls the original exportCSV/exportPDF
    unchanged.
  - new `exporting` state disables the button and shows "Exporting…"
    while a download is in flight, and surfaces a real error message on
    failure instead of failing silently.
  - the one hardcoded "Floor roster" empty-state string now reads
    "Kitchen roster" when the department code is KITCHEN.

- data/constants.js:
  - ENGINE_DEPARTMENT_CODES: added "KITCHEN" — the only line that makes
    Kitchen use the backend scheduling engine instead of the client-side
    generator; FloorRosterTable, ValidationPanel, and
    FloorSettingsPanel needed zero changes to work for Kitchen, since
    none of them contained Floor-specific logic to begin with (updated
    their doc comments to say so, no behavior changed).
  - DEPARTMENT_POSITIONS.KITCHEN: replaced the placeholder role list
    ("Kitchen Supervisor"/"Head Chef"/"Sous Chef"/"Line Cook"/"Kitchen
    Porter") with the six sections from the Arami Kitchen Schedule
    reference image — Hot Section, Salad & Dessert, Bakery, Chinese
    Section, Sushi Section, Butcher — matching what the backend's
    Kitchen coverage-rule catalog actually seeds. Any existing Kitchen
    staff record using the old position names will need updating to one
    of the new section names, or the backend's new role-assignment
    validation check will flag it rather than silently misscheduling
    them.
  - POSITION_COLORS: updated the Kitchen color block's keys to match
    the new section names (same red/orange family, plus a new
    magenta/purple entry for Sushi Section).

No new routes were added — exports still trigger from the existing
roster page; Kitchen reuses every roster-engine component Floor already
had.
